## 1. The problem

An exam result system takes a roll number and returns the result.

That sounds simple. Two things make it genuinely hard at scale:

1. **The Thundering Herd.** Millions of students open *"my result"* simultaneously on a known, highly anticipated day.
   Traffic goes from zero to millions of requests per second the exact second the clock strikes the publishing hour.
2. **The Result Never Changes.** Once published, an individual student's marks and status are static and immutable. This
   makes it an ideal candidate for heavy caching, meaning the database should barely be touched during peak hours.

Everything in this doc is one design decision in service of those constraints, focusing entirely on the high-concurrency
**read path**.

---

## 2. The read path

Every request the system handles during release day is the same: **a student submits their roll number and gets back
their scorecard.**

Because results are static, reads happen intensely within a short window. The design leans heavily on an in-memory cache
so that almost every request is served instantly without burdening the database.

## 4. The database schema

Marks are stored as key-value pairs in a `JSONB` column. The total is computed once in the application code on a cache
miss and cached alongside the row, keeping database reads trivial.

```sql
CREATE TABLE exam_results
(
    roll_no      BIGINT PRIMARY KEY,  -- lookup key (PK ⇒ already indexed)
    student_name TEXT       NOT NULL,
    marks        JSONB      NOT NULL, -- {"mathematics":87,"physics":72,...}
    status       VARCHAR(4) NOT NULL, -- 'PASS' | 'FAIL'
    published_on DATE       NOT NULL
);

```

A stored row looks like:

```json
{
  "roll_no": 4231765,
  "student_name": "Rajesh Kumar Verma",
  "marks": {
    "mathematics": 87,
    "physics": 72,
    "chemistry": 90,
    "english": 78,
    "computer_science": 95,
    "hindi": 81
  },
  "status": "PASS",
  "published_on": "2026-05-20"
}

```

## 6. Sizing database connections and app threads with Little's Law

Before touching disk or memory sizes, we must determine how many database connections and concurrent app threads are
required to handle our target throughput of **1,000 requests per second** using **Little's Law**
($L = \lambda \times W$).

### 6.1 The Timing Assumption

Assume a single point read takes an idle latency of **$\approx 2\text{ ms}$** ($0.002\text{ seconds}$) for a warm index
scan or Redis key lookup.

### 6.2 Sizing Database Connections

During steady-state operation with a ~99% cache hit rate, only 1% of the 1,000 rps misses Redis and hits Postgres
($\lambda_{\text{db}} = 10\text{ queries/sec}$). However, to safely size for the initial cold-cache thundering herd
where the cache is empty and incoming requests temporarily hit Postgres directly at 1,000 rps:

* **Arrival Rate ($\lambda_{\text{db}}$):** 1,000 queries/sec hitting the database.
* **Hold Time ($W$):** ~2 ms ($0.002\text{ seconds}$) per warm index lookup.

Applying Little's Law:

```
DB connections in flight  =  Arrival Rate (λ) × Hold Time (W)
                          =  1,000/sec × 0.002s
                          =  2 active connections in flight

```

Applying headroom ($\times 2$ for burst absorption):

* **Database Connection Pool:** ~4 active connections are required. We configure a pool of **~20 connections** (via
  PgBouncer) to provide a safe buffer for tail latencies while keeping resource consumption well below Postgres limits.

### 6.3 Sizing App-Level Threads

* **Arrival Rate ($\lambda$):** 1,000 requests/sec arriving at the application layer.
* **Hold Time ($W$):** ~2 ms ($0.002\text{ seconds}$) spent per request lifecycle.

Applying Little's Law:

```
App threads in flight  =  Arrival Rate (λ) × Hold Time (W)
                       =  1,000/sec × 0.002s
                       =  2 active threads in flight on average

```

*Note on Provisioning:* While only 2 threads are mathematically busy on average to sustain 1,000 rps, standard web
frameworks (like Tomcat) ship with a default pool of **200 worker threads**. This pool size does *not* mean 200
requests/sec; rather, those extra threads act as "spare chairs" to absorb network jitter, client-side latency tails, and
sudden burst waves without rejecting connections.

## 7. Database disk sizing

Disk storage starts from the size of a single row.

**Rule:** `one row × students × 3`.

* Seed: **one row ≈ 0.5 KB** (accounting for tuple headers, student name, JSONB marks, status, and publish date).
* Multiply by 50 lakh (5,000,000) students, then pad **×3** for Postgres per-row bookkeeping, unpacked pages, and the
  roll index:

$$\text{Disk Space} = 0.5 \text{ KB} \times 5,000,000 \times 3 \approx \mathbf{7.5 \text{ GB}}$$

---

## 8. Database RAM sizing

To ensure that index lookups and hot result rows remain in memory without triggering disk I/O bottlenecks, we size RAM
to comfortably hold the working set plus system headroom ($\times 2$ rule):

$$\text{Database RAM} \approx 7.5 \text{ GB} \times 2 \approx \mathbf{16 \text{ GB box}}$$

---

## 9. Redis RAM sizing

Since Redis caches results to achieve a ~99% cache hit rate during the release window, it needs to hold results for
active student requests.

**Rule:** `students × size-of-one-result × 2`.

$$\text{Redis Memory} = 5,000,000 \text{ records} \times 0.5 \text{ KB per payload} \times 2 \approx \mathbf{5 \text{ GB}}$$

---

## 10. Protecting the database from traffic spikes

If a cache key expires or a wave of unique requests hits simultaneously, a short-lived distributed lock in Redis
prevents cache stampedes:

```
SET lock:result:{roll_no} NX EX 2

```

The first request acquires the lock, queries Postgres, populates Redis, and releases it. Concurrent requests wait
briefly (20–50ms) and retry the cache, receiving the populated payload without burdening the database.

---

## 11. Scaling order

When traffic grows, scale in this strict order:

1. **Redis Caching Layer:** Add read replicas to distribute memory-read bandwidth.
2. **Stateless App Instances:** Horizontally scale app instances behind a load balancer.
3. **Database Read Replicas:** Route any administrative queries or cold-cache fallbacks to Postgres read replicas.

---

## 12. How to build this in stages

1. **V1 — Core Functionality:** Single Postgres instance, single Redis node, and a basic endpoint executing point
   lookups by roll number.
2. **V2 — Caching & Protection:** Implement cache-aside patterns in the application code with a 24-hour TTL, along with
   cache-stampede locks.
3. **V3 — High Availability:** Deploy Redis clusters/sentinel and configure PgBouncer to manage database connection
   thresholds cleanly.

---

## 13. One-paragraph summary

The hard part of designing an exam result publication system is surviving the massive surge of students checking their
scores at the exact same second without crushing the database. This design solves the problem by treating published exam
rows as immutable data and caching them aggressively in Redis for 24 hours. On release day, the read path uses Little's
Law to size both database connection pools and application thread pools precisely, bypassing relational database compute
entirely for ~99% of requests while serving the rest via rapid single-row index lookups.
