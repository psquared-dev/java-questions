# Parking Lot LLD – Database Design and Core SQL

## 1. Database Design

PostgreSQL relational database. Active and historical parking sessions are stored in the same `parking_ticket` table.

### 1.1 `parking_lot`

| Column | Type         | Constraint   |
|--------|--------------|--------------|
| id     | BIGINT       | PK, identity |
| name   | VARCHAR(100) | NOT NULL     |
| active | BOOLEAN      | NOT NULL     |

### 1.2 `parking_floor`

| Column         | Type         | Constraint           |
|----------------|--------------|----------------------|
| id             | BIGINT       | PK, identity         |
| name           | VARCHAR(100) | NOT NULL             |
| floor_number   | INTEGER      | NOT NULL             |
| active         | BOOLEAN      | NOT NULL             |
| parking_lot_id | BIGINT       | FK → parking_lot(id) |

Unique constraint: `(parking_lot_id, floor_number)`

`name` is the display name, such as Ground Floor or Basement 1. `floor_number` is used for ordering and tie-breaking.

### 1.3 `parking_spot`

| Column           | Type        | Constraint             |
|------------------|-------------|------------------------|
| id               | BIGINT      | PK, identity           |
| section          | VARCHAR(20) |                        |
| spot_number      | VARCHAR(20) | NOT NULL               |
| spot_type        | VARCHAR(30) | NOT NULL               |
| active           | BOOLEAN     | NOT NULL               |
| parking_floor_id | BIGINT      | FK → parking_floor(id) |

`spot_type`: `CAR`, `TWO_WHEELER`

Unique constraint: `(parking_floor_id, section, spot_number)`

`active` indicates whether the spot is operational. Occupancy is derived from active tickets; there is no `occupied`
column.

### 1.4 `gate`

| Column         | Type        | Constraint           |
|----------------|-------------|----------------------|
| id             | BIGINT      | PK, identity         |
| gate_number    | VARCHAR(20) | NOT NULL             |
| gate_type      | VARCHAR(20) | NOT NULL             |
| active         | BOOLEAN     | NOT NULL             |
| parking_lot_id | BIGINT      | FK → parking_lot(id) |

`gate_type`: `ENTRY`, `EXIT`

A parking lot can have multiple gates.

### 1.5 `parking_ticket`

| Column              | Type        | Constraint            |
|---------------------|-------------|-----------------------|
| id                  | BIGINT      | PK, identity          |
| registration_number | VARCHAR(30) | NOT NULL              |
| vehicle_type        | VARCHAR(30) | NOT NULL              |
| parking_spot_id     | BIGINT      | FK → parking_spot(id) |
| entry_gate_id       | BIGINT      | FK → gate(id)         |
| exit_gate_id        | BIGINT      | FK → gate(id), NULL   |
| entry_time          | TIMESTAMP   | NOT NULL              |
| exit_time           | TIMESTAMP   | NULL                  |
| active              | BOOLEAN     | NOT NULL              |

Vehicle details are stored in the ticket table; there is no separate vehicle table.

`active = TRUE` means the vehicle is currently parked. Historical tickets remain in this table with `active = FALSE`.

### 1.6 `payment`

| Column                | Type          | Constraint              |
|-----------------------|---------------|-------------------------|
| id                    | BIGINT        | PK, identity            |
| ticket_id             | BIGINT        | FK → parking_ticket(id) |
| amount                | NUMERIC(12,2) | NOT NULL                |
| payment_method        | VARCHAR(20)   | NOT NULL                |
| payment_status        | VARCHAR(20)   | NOT NULL                |
| transaction_reference | VARCHAR(100)  | NULL                    |
| created_at            | TIMESTAMP     | NOT NULL                |
| updated_at            | TIMESTAMP     | NOT NULL                |

`payment_method`: `CASH`, `CARD`, `UPI`

`payment_status`: `PENDING`, `SUCCESS`, `FAILED`

One ticket can have multiple payment attempts. A retry creates a new payment record.

## 2. Entity Relationships

- `ParkingLot` 1 → N `ParkingFloor`
- `ParkingLot` 1 → N `Gate`
- `ParkingFloor` 1 → N `ParkingSpot`
- `ParkingSpot` 1 → N `ParkingTicket` (historical sessions)
- `Gate` 1 → N `ParkingTicket` through `entry_gate_id`
- `Gate` 1 → N `ParkingTicket` through `exit_gate_id`
- `ParkingTicket` 1 → N `Payment`

## 3. Important Indexes and Constraints

Only one active ticket per vehicle:

```sql
CREATE UNIQUE INDEX uk_active_vehicle
    ON parking_ticket (registration_number) WHERE active = TRUE;
```

Only one active ticket per parking spot:

```sql
CREATE UNIQUE INDEX uk_active_spot
    ON parking_ticket (parking_spot_id) WHERE active = TRUE;
```

Support lookup of active tickets by spot:

```sql
CREATE INDEX idx_ticket_active_spot
    ON parking_ticket (parking_spot_id) WHERE active = TRUE;
```

These partial unique indexes enforce the active-ticket rules while allowing historical tickets to remain.

## 4. Parking Spot Allocation

Allocation policy: choose the floor with the lowest occupancy percentage for the required spot type. Then find a free
spot of that type on the selected floor.

The ticket table is the source of truth for occupancy: a spot is occupied when an active ticket references it.

### 4.1 Find floors with free spots

This is the floor availability query:

```sql
SELECT pf.id        AS parking_floor_id,
       COUNT(ps.id) AS free_parking_spots
FROM parking_floor pf
         INNER JOIN parking_spot ps
                    ON pf.id = ps.parking_floor_id
         LEFT JOIN parking_ticket pt
                   ON pt.parking_spot_id = ps.id
                       AND pt.active = TRUE
WHERE pt.id IS NULL
GROUP BY pf.id
ORDER BY free_parking_spots;
```

### 4.2 Find and lock a free spot on the selected floor

Example: find a free `CAR` spot on floor `3`.

```sql
SELECT ps.*
FROM parking_spot ps
         LEFT JOIN parking_ticket pt
                   ON ps.id = pt.parking_spot_id
                       AND pt.active = TRUE
WHERE ps.parking_floor_id = 3
  AND ps.active = TRUE
  AND pt.id IS NULL
  AND ps.spot_type = 'CAR' LIMIT 1
FOR
UPDATE OF ps SKIP LOCKED;
```

Execute this query inside the same database transaction as ticket creation.

- `LEFT JOIN ... pt.active = TRUE` checks only current parking sessions.
- `pt.id IS NULL` keeps spots without an active ticket.
- `LIMIT 1` selects one candidate spot.
- `FOR UPDATE OF ps` locks the selected spot row.
- `SKIP LOCKED` skips a candidate already locked by another transaction.

## 5. Vehicle Entry Flow

Execute the database operations below in **one transaction**.

```sql
BEGIN;

-- Step 1: Check whether this vehicle already has an active parking ticket.
SELECT id
FROM parking_ticket
WHERE registration_number = :registrationNumber
  AND active = TRUE;

-- If a row exists, reject the entry request.

-- Step 2: Find floors with free spots.
-- Use the floor-availability query from Section 4.1.
-- Apply the agreed floor-selection strategy to its result.

-- Step 3: Find and lock one free spot of the required vehicle type
-- on the selected floor.
-- Use the query from Section 4.2, supplying :floorId and :vehicleType.
-- If no row is returned, try the next eligible floor.

-- Step 4: Create the active parking ticket for the locked spot.
INSERT INTO parking_ticket (registration_number,
                            vehicle_type,
                            parking_spot_id,
                            entry_gate_id,
                            entry_time,
                            active)
VALUES (:registrationNumber,
        :vehicleType,
        :spotId,
        :entryGateId,
        CURRENT_TIMESTAMP,
        TRUE) RETURNING *;

-- Step 5: Commit the ticket and spot allocation together.
COMMIT;
```

If any step fails, roll back the transaction. The row lock is released and no ticket is created.

## 6. Vehicle Exit Flow

Payment must succeed before the parking session is closed and the spot becomes available.

### Step 1: Retrieve the active ticket and calculate the fee

```sql
-- Retrieve the active parking ticket.
SELECT *
FROM parking_ticket
WHERE id = :ticketId
  AND active = TRUE;
```

Calculate the fee using the ticket's entry time, the current time, and the vehicle type.

### Step 2: Initiate payment

Call the payment service or external payment gateway **outside a database transaction**. Do not keep a database
transaction open while waiting for the gateway response.

### Step 3: Record the payment result and close the session on success

After receiving the payment result, execute the following in one database transaction:

```sql
BEGIN;

-- Step 3a: Lock and revalidate the active ticket.
SELECT id
FROM parking_ticket
WHERE id = :ticketId
  AND active = TRUE
    FOR UPDATE;

-- If no row is returned, do not close the session.

-- Step 3b: Record the payment attempt and its result.
INSERT INTO payment (ticket_id,
                     amount,
                     payment_method,
                     payment_status,
                     transaction_reference,
                     created_at,
                     updated_at)
VALUES (:ticketId,
        :amount,
        :paymentMethod,
        :paymentStatus,
        :transactionReference,
        CURRENT_TIMESTAMP,
        CURRENT_TIMESTAMP) RETURNING id;

-- Step 3b: Close the parking session only if payment succeeded.
-- A failed payment leaves the ticket active and the spot occupied.
UPDATE parking_ticket
SET exit_gate_id = :exitGateId,
    exit_time    = CURRENT_TIMESTAMP,
    active       = FALSE
WHERE id = :ticketId
  AND active = TRUE
  AND :paymentStatus = 'SUCCESS';

-- Step 3c: Commit the payment result and, on success, session closure together.
COMMIT;
```

A failed payment attempt is still recorded, but the ticket remains active. A retry creates another payment attempt. The
spot becomes available when the active ticket is closed after successful payment.

## 6. Transaction Boundaries and Concurrency

| Flow          | Transaction boundary                                                                                                                                                               |
|---------------|------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Vehicle entry | One transaction: check active vehicle → find floor → lock spot → insert ticket → commit                                                                                            |
| Vehicle exit  | Read active ticket → calculate fee → call payment gateway outside a transaction → one transaction: lock/revalidate ticket, record payment result, and close ticket only on success |

Key points:

1. `FOR UPDATE SKIP LOCKED` skips a spot row already locked by another transaction.
2. The unique partial index on active `parking_spot_id` prevents duplicate active allocation.
3. The unique partial index on active `registration_number` prevents a vehicle from having multiple active tickets.
4. If ticket creation fails, the entry transaction rolls back and releases the row lock.
5. Do not hold a database transaction open while calling an external payment gateway.
6. The ticket is closed only after successful payment; a failed payment leaves the ticket active and the spot occupied.
